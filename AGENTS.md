# AGENTS.md

Инструкции для ИИ-агентов, работающих в репозитории webShopProject.

## Начало и завершение работы

При начале каждой сессии агент обязан:

1. Обновить код из репозитория: `git checkout main && git pull --ff-only`.
2. Проанализировать код проекта и спецификации (`openspec/specs/`) и быть готовым к получению задачи.

После реализации задачи и закрытия сессии агент всегда переключается обратно на ветку `main`.

## Git workflow (обязательно)

Все изменения вносятся **только через отдельную ветку + merge request**:

1. Перед началом работы создать ветку от `main`: `git checkout main && git pull --ff-only && git checkout -b <branch-name>`
   - Именование веток: `<type>/<описание>`, например `iss/fix/доработка-pom-в-сервисах-auth-и-product-notask`.
   - `<type>`: `fix`, `feat`, `chore`, `docs`, `spec` и т.п. (совпадает с типом conventional-коммита). `docs` — для изменений в документации и `.md`-файлах, `spec` — для изменений в спецификациях. Префикс `iss/` — если задача связана с задачей в трекере.
2. Название ветки и текст каждого коммита **сначала предоставляются пользователю на утверждение**. Только после утверждения — коммитить, пушить и оформлять MR/PR.
3. Коммитить изменения только в этой ветке.
4. Если в ветке несколько коммитов — при merge применяется **squash**, чтобы в итоге на одну задачу приходился один коммит. Текст итогового коммита должен быть общим и отражать все изменения задачи.
5. После завершения работы — запушить ветку и оформить MR/PR.
6. Свои коммиты в `main` напрямую — запрещены.

## OpenSpec change-цикл (протокол сессии)

Все изменения спецификаций ведутся только через полноценный change-цикл OpenSpec (CLI `openspec` >= 1.13, схема `spec-driven`). Команды жизненного цикла — slash-команды OpenCode, вводятся в чате: `/opsx-propose`, `/opsx-apply`, `/opsx-sync`, `/opsx-archive`.

**Порядок (каждый шаг):** агент **подсказывает** команду -> пользователь вводит её в чате -> только тогда агент выполняет работу и показывает результат (`git diff` / вывод проверок) -> ждёт подтверждения «всё ли ок».

0. Планирование. Когда план согласован и предстоят изменения, агент обязан подсказать, как выйти из режима плана: **нажать `Tab`** (переключение режимов Plan <-> Build, индикатор — правый нижний угол) и подтвердить старт реализации.
1. План согласован. Подсказка: `/opsx-propose <id>` (kebab-case). Агент создаёт change и наполняет артефакты (proposal, design, tasks, `specs/<capability>/spec.md` — delta), показывает.
2. Утверждение артефактов (или правки по замечаниям).
3. Подсказка: `/opsx-apply`. Агент реализует код и актуализирует delta-спеки, показывает `git diff`. Контроль: `openspec status --change "<id>" --json`, `mvn clean package`.
4. Подсказка: `/opsx-sync`. Агент интеллектуально сливает delta в `openspec/specs/`, показывает diff. Контроль: `openspec validate --specs`.
5. Подсказка: `/opsx-archive`. Агент архивирует в `openspec/changes/archive/`, проверяет, показывает.
6. Агент предлагает ветку + текст коммита -> утверждение -> коммит, push, MR.
7. После merge ветка удаляется (в репо только `main`).

**Правила:**
- Нет заархивированного change -> нет MR, затрагивающего спеку. Ручные правки `openspec/specs/` мимо changes/ и ретроспективный архив запрещены.
- `apply`/`sync` не существуют как подкоманды `openspec` CLI: `/opsx-apply` и `/opsx-sync` — slash-команды OpenCode (скиллы `.opencode/skills/`), выполняет агент. `openspec archive` сам обновляет главные спеки.
- Спека попадает в архив до MR: правки спеки на ревью MR — только через новый change.
- Код/документация без влияния на спеки — обычный Git-процесс без change.

## Структура проекта

- Мультимодульный Maven-проект (Java 25, Spring Boot 4.0.6).
- Родительский `pom.xml` централизует общую конфигурацию: версии зависимостей в `dependencyManagement`, плагины в `pluginManagement` (см. `openspec/specs/build-configuration/spec.md`).
- Дочерние модули: `backend/auth-service`, `backend/product-service` — только подключают общую конфигурацию, не дублируют её.
- Спецификации проекта живут в `openspec/specs/` (OpenSpec). Промежуточные правки ведутся через `openspec/changes/` (см. раздел «OpenSpec change-цикл»).

## Прочее

- Язык коммитов и комментариев — русский.
- Коммит-сообщения по conventional commits: `fix(...)`, `feat(...)`, `chore(...)`, `docs(...)`, `spec(...)` и т.п.
- Номер задачи (`#<номер>`) в ветке и коммите используется **только когда пользователь его сообщит**. По умолчанию всегда ставь `#notask`.
