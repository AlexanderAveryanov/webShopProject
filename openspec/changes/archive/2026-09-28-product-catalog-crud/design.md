# Design

## Context

See proposal.md - Why for the motivation. What shapes the approach technically:

- The feature branch `iss/feat/Создание-сущностей-для-product-service-8` already contains the `Category` and `Product` entities, the four DTOs, both repositories and two draft migrations, plus two empty controller stubs. There is no service, exception or security layer, and nothing in the branch compiles against a running service.
- product-service has no Spring Security dependency and no security configuration at all; auth-service does, with a hand-written `JwtAuthenticationFilter` that resolves the user from its own `users` table to obtain the role.
- `ddl-auto: validate` and `baseline-on-migrate: true` are set in product-service, matching auth-service; `product_db` is exposed on host port 5433 by `postgres-product` in docker-compose.
- auth-service is the reference for conventions: constructor injection, `ResponseEntity<T>` bodies without an envelope wrapper, `@Data @Builder @NoArgsConstructor @AllArgsConstructor` on DTOs, `@Getter @Setter` on entities, manual DTO-to-entity mapping inside the service, a `ErrorResponse` DTO plus `@RestControllerAdvice`, and Russian validation messages.
- The `user-auth` spec already requires case-insensitive uniqueness for email, realised as a unique index on `LOWER(email)`.
- `JwtTokenProvider.generateToken` writes only `sub`, `iat` and `exp` into the token, signed with HS256 using the `jwt.secret` value, and its lifetime defaults to 24 hours.
- No tests exist anywhere in the repository and neither module depends on a test starter, so verification is `mvn clean package` plus manual request checks.
- No users exist in `auth_db` and no rows exist in `product_db`.

## Goals / Non-Goals

**Goals:**
- Make the catalog work end to end: the tables exist, every endpoint of the task is implemented, and the service starts.
- Make the role column of the task enforceable inside product-service while keeping the service autonomous (no request-time dependency on auth-service, no user data in `product_db`).
- Reuse the auth-service response, error-handling and mapping conventions instead of inventing a product-specific dialect.
- Keep the entity, the DTO validation and the Flyway schema in agreement, so `ddl-auto: validate` and bean validation report real problems only.

**Non-Goals:**
- Pagination of catalog listings. The requirement is specced, the implementation is a follow-up change; listing endpoints stay unpaginated here.
- Provisioning the first ADMIN account (bootstrap runner, role promotion). A manual SQL step covers verification of the ADMIN endpoints in this change; the capability itself is a separate change.
- Introducing MapStruct. It is listed in the README but absent from the parent POM, so manual mapping stays, consistent with auth-service.
- A shared module for `ErrorResponse` and `GlobalExceptionHandler`, which are duplicated between the two services for now.
- Immediate token revocation. Asymmetric signing is in scope here, revocation is not: a token already issued to a user who has since been deleted stays usable in product-service until it expires.
- Seed data for the catalog, product attributes (sizes, colours), search and sorting. Only the category filter from the task is implemented.

## Decisions

- **The role travels in the token, product-service verifies it locally.** `JwtTokenProvider.generateToken` takes the authenticated user and writes a `role` claim. product-service becomes an OAuth2 resource server: `spring-boot-starter-oauth2-resource-server` plus `issuer-uri` and `jwk-set-uri` properties, and a `JwtAuthenticationConverter` that turns the claim into authorities; method security then enforces the roles.
  *Alternatives considered:* gateway-only enforcement (the gateway does not exist yet, and it would leave the service unprotected when addressed directly on port 8082); RFC 7662 introspection or a call to auth-service (reintroduces inter-service coupling and makes the catalog unavailable whenever auth-service is down, which contradicts one-database-per-service); replicating users into `product_db` (a second source of truth for a fact the token already carries); a hand-written filter on jjwt, the way auth-service does it (duplicates token parsing and its bug surface).
- **Tokens are signed with RS256, and the verifying service gets only the public key.** auth-service keeps a private key, signs with it, and publishes the public part at `/.well-known/jwks.json`; product-service verifies tokens with the stock `spring.security.oauth2.resourceserver.jwt` properties instead of a hand-written decoder. Both `issuer-uri` and `jwk-set-uri` are set: the issuer claim is still validated, but Spring skips the OIDC discovery call, so product-service starts even when auth-service is temporarily down.
  *Alternatives considered:* keeping the shared HS256 secret (fewer moving parts, but every service holding the secret can also mint an ADMIN token, and jjwt picks the algorithm from the key length, so the two services can end up on different algorithms and verification fails with an opaque error instead of a clear one). Switching to jjwt inside auth-service while product-service used Spring was rejected: two JWT libraries in one service for no benefit, so jjwt was removed from auth-service in favour of `NimbusJwtEncoder`/`NimbusJwtDecoder`.
- **The key pair is generated on first start and stored outside git.** `JwtKeyConfig` writes `private.pem` and `public.pem` into `jwt.keys-dir` (default `keys`, overridable with `JWT_KEYS_DIR`) on first start and reads them afterwards, so already issued tokens survive a restart. The `kid` is the RFC 7638 thumbprint of the public key, so it is stable across restarts and matches the JWKS. `keys/` is gitignored.
  *Alternatives considered:* committing PEM files (the private key would enter the repository history permanently); passing the key through an environment variable (awkward for a multi-line PEM and for docker-compose); generating an ephemeral pair on every start (would invalidate all tokens on every restart).
- **The token lifetime is 15 minutes.** A deleted user keeps access in product-service for at most the remaining lifetime of the issued token, and there is no way to revoke earlier without a request-time call to auth-service. The next task introduces a Redis-based revocation check; the 15-minute window is what that task has to cover.
  *Alternatives considered:* keeping 24 hours (a long window in which a deleted user still acts); RFC 7662 introspection (revocation is immediate, but every request becomes an HTTP call to auth-service and the local signature check is replaced by a remote one).
- **The claim holds the plain role value (`"ADMIN"`), the service adds the `ROLE_` prefix.** `JwtGrantedAuthoritiesConverter.setAuthoritiesClaimName("role")` with `setAuthorityPrefix("ROLE_")` produces the same `ROLE_ADMIN` authority that `JwtAuthenticationFilter` builds in auth-service, so both services use `hasRole('ADMIN')` and stay consistent. Keeping the token free of the framework prefix means a future external identity provider can add its own claim names without ambiguity, and keeps roles distinguishable from OAuth2 scopes (`SCOPE_`), which would be the default prefix.
- **Migrations are renamed to `V1__create_categories_table.sql` and `V2__create_products_table.sql`.** Flyway's SQL migration separator is a double underscore: files named with a single underscore are silently skipped instead of failing, so the branch currently produces an empty schema and `ddl-auto: validate` then aborts startup on a missing table. The version split follows the foreign key - `products.category_id` references `categories(id)`, so categories must be created first.
- **Deleting a category deletes its products, and the confirmation belongs to the client.** `CategoryService.delete` calls `productRepository.deleteAllByCategoryId(id)` and then deletes the category, both inside the class-level transaction, so the operation is atomic: either both are gone or nothing changed. The entity's `CascadeType.ALL` is removed - on the inverse (`mappedBy`) side of a one-to-many JPA does not honour a remove cascade anyway, so the line promised behaviour the mapping never provided, and the `ON DELETE RESTRICT` in the migration is what would actually have fired.
  *Alternatives considered:* rejecting the delete with HTTP 409 while the category is not empty (safe, but pushes the cleanup onto the user and needs a second round of calls); `ON DELETE CASCADE` in the migration (one statement instead of two, but the cascade becomes invisible in the code and would also fire for a direct SQL `DELETE`); `CascadeType.REMOVE` on the entity (does not work on the inverse side, would require restructuring the mapping). Confirming the consequence in the frontend keeps the server free of a confirmation parameter: the client asks, the user answers, the same `DELETE` is sent.
- **Category names are unique case-insensitively.** The migration adds a unique index on `LOWER(name)`, the service checks `existsByNameIgnoreCase` before insert and update, and the database constraint remains the backstop. This mirrors the `LOWER(email)` index already required by `user-auth`, so `"Джинсы"` and `"джинсы"` cannot become two categories. *Alternative considered:* the plain `UNIQUE` of the task description, which treats them as distinct names.
- **A category update that keeps its own name is allowed.** The uniqueness check excludes the category being updated, so a rename that does not change the name (including its letter case) is not a conflict.
- **Validation limits are derived from the column widths, and the entity declares them.** `CategoryRequest.name` gets `@Size(max = 100)` to match `VARCHAR(100)` (it currently says 50), `ProductRequest.name` `@Size(max = 255)` for `VARCHAR(255)`, `imageUrl` `@Size(max = 500)`, `price` `@Positive` plus `@Digits(integer = 8, fraction = 2)` for `DECIMAL(10,2)`, `stockQuantity` `@PositiveOrZero`, and the entity columns get explicit `length` values. This is the same defect class that PR #22 fixed in auth-service: a value that passes bean validation and fails in the database is reported as an integrity violation instead of a field error.
- **`PATCH /api/products/{id}/stock` sets an absolute value and returns the full product.** The body carries the resulting `stockQuantity`, which replaces the stored value; the response is the complete `ProductResponse` so the admin UI can re-render the card without a second request.
  *Alternatives considered:* a delta body (reads like a warehouse operation, but two concurrent updates lose one of the changes and the server must compute against the current value); 204 with no body (formally cleaner, but the caller has to fetch the product again to show the new figure).
- **Mapping is written by hand inside each service, as in auth-service.** `CategoryService` and `ProductService` map entity to DTO with setters and DTO to entity with setters. The DTOs already carry `@Builder`, but auth-service builds responses with setters, so the services follow it. `ProductResponse.categoryId` is the category id, read from the lazy proxy inside the service's transaction; the category's products are never mapped into a response, so no extra query is triggered.
- **The service layer is transactional at class level.** Both services are annotated `@Service @Transactional`; writes are covered by the same annotation, and the lazy category is read while the transaction is open. No `open-in-view` setting is introduced.
- **Errors are reported through a product-local `ErrorResponse` and `GlobalExceptionHandler`**, copied from auth-service's shape: `CategoryNotFoundException` and `ProductNotFoundException` for 404, `CategoryAlreadyExistsException` for 409, `MethodArgumentNotValidException` for 400 with a field-to-message map, `MethodArgumentTypeMismatchException` and `HttpMessageNotReadableException` for 400, `DataIntegrityViolationException` for 409, and a catch-all 500 that logs the cause. Cross-service duplication is accepted temporarily, exactly as `mapToUserResponse` duplication was accepted when the admin panel was added.
- **An unknown `categoryId` in the product list filter yields an empty list.** The filter is a listing convenience, not an existence check, so it does not require a category lookup. The same value in a create or update body is a different matter and is rejected with 404, because the reference cannot be satisfied.
- **CORS configuration is replicated from auth-service** for the development frontend ports (3000, 5173, 8080) with the `Authorization` header allowed, since the catalog is called with a bearer token. The allowed-methods list gains `PATCH` for the stock endpoint.
- **Repository methods follow the actual uniqueness of the columns.** `findByName` and `existsByName` are removed from `ProductRepository` - `products.name` is not unique, so those methods imply a uniqueness that does not exist. `findByCategoryId` is kept, and `deleteAllByCategoryId` is added for the category delete; both are written as explicit `@Query` methods because the association field is `categoryId` of type `Category` and the derived-name parser would need an extra hop to reach the id.
- **The first ADMIN is created by a manual SQL step during verification, not by a migration.** No user can obtain the ADMIN role through the API: registration always assigns USER and the admin endpoints only read. Seeding credentials from a Flyway migration is rejected because the password hash would enter the repository permanently and could never be rotated, and because the same migration would apply the same account to every environment. A follow-up change adds an idempotent bootstrap runner that reads the account from the environment and only acts when no ADMIN exists, plus role promotion as a separate administrative capability.

## Risks / Trade-offs

- [Risk] The role in the token is a snapshot, so promoting or demoting a user has no effect until the token expires (15 minutes by default) → acceptable for the catalog; a promotion takes effect at the next login.
- [Risk] product-service cannot detect a deleted or demoted user before the token expires, because it has no user record to check → inherent to a stateless resource server; the 15-minute lifetime bounds the window, and the Redis-based revocation of the next task is what removes the window entirely.
- [Trade-off] The private key is a local file, so the auth-service node must keep it: losing `keys/private.pem` invalidates every issued token, and a cluster would need shared storage for it. A managed key store is the answer once the service runs in more than one instance.
- [Trade-off] `ErrorResponse` and the exception handler are duplicated across services, and DTO mapping is duplicated as well → accepted to avoid introducing a shared module or MapStruct in this change; both are candidates for a dedicated change.
- [Trade-off] `products.name` is not unique, so two products may share a name → follows the task description; a uniqueness rule would need a product-level requirement.
- [Risk] Deleting a category now removes its products in the same call → the confirmation is the frontend's job, so a client that sends `DELETE` without asking loses products. The trade-off was chosen deliberately: the data is reachable again by re-creating the products, and a rejected delete would have needed a second, more dangerous call anyway.
- [Risk] The migrations of this change were already applied to the local `product_db` while they were being edited, so Flyway refused to validate until the local schema was recreated → harmless here because the schema was never released anywhere, but it is the reason an applied migration file must not be edited after it ships.
- [Risk] `GET /api/categories` sits outside the `/api/products/**` route documented in the README for the API gateway → when the gateway is implemented it must route both prefixes; recorded for that change, no path is changed here because the task fixes the URLs.
- [Risk] No automated tests cover any of this, because the repository has no test infrastructure → verification is `mvn clean package` plus the manual request matrix in tasks.md; introducing a test starter is a separate concern.

## Migration Plan

- No data migration is required. `product_db` has no tables and no rows, and the two migrations create the schema from scratch. `auth_db` is not touched at all; the change adds no column and no table there.
- No token back-compatibility is required. No users exist, so no tokens have been issued. Every token issued before the RS256 switch is signed with a different algorithm and will be rejected, so any existing session has to log in again. The same applies to a restarted auth-service whose `keys/` directory was lost: the public key changes and old tokens stop verifying.
- Deploy order: auth-service first (it starts signing with RS256 and publishing JWKS), then product-service. Deploying product-service first would leave it unable to fetch a key set and every token rejected, so the order is the other way round from a symmetric setup, where the issuer had to ship the claim first.
- Verification prerequisite: promote a test account with `UPDATE users SET role = 'ADMIN' WHERE email = '<test user>'` in `auth_db`, since no user can obtain that role through the API. Registered users can only exercise the read paths.
- Rollback: revert both modules. The migrations are additive, so the `categories` and `products` tables and the unique index can be left in place; the next deployment reuses them because `flyway_schema_history` still records the applied versions.

## Open Questions

- Whether the API gateway will route `/api/categories` in addition to the documented `/api/products/**`, or whether the category endpoints should eventually live under the product prefix. Decided for now by the task's URLs; the answer does not change this implementation.
- Whether the bootstrap of the first ADMIN and role promotion are delivered as one change or two, and whether the account comes from the environment or from a secret store. Does not affect this change.
