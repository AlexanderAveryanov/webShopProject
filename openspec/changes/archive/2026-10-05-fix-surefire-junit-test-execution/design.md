# Design

## Context

Текущее состояние сборки (проверено командами, не предположение):

- Тесты написаны на JUnit Jupiter 6.0.3. Версия приходит транзитивно из `spring-boot-starter-test` (Spring Boot BOM 4.0.6) и явно в проекте не зафиксирована.
- `maven-surefire-plugin` не объявлен ни в родительском `pom.xml`, ни в дочерних модулях. Maven 3.8.7 подставляет версию 2.12.4 из своего супер-POM.
- Наблюдаемое следствие: `mvn clean test` завершается `BUILD SUCCESS` с `Tests run: 0` в обоих модулях.

Ключевой момент, определяющий подход: Spring Boot BOM 4.0.6 задаёт в своём `pluginManagement` версию surefire `3.5.5`, но она **не попадает** в наш проект. Импорт BOM оформлен как `<scope>import</scope>` внутри `dependencyManagement`, а такой импорт переносит только раздел `dependencyManagement`. Раздел `pluginManagement` при импорте BOM не наследуется.

Проверено командой `mvn help:effective-pom` на исходном (неизменённом) `pom.xml`:
```xml
<artifactId>maven-surefire-plugin</artifactId>
<version>2.12.4</version>
```
а не `3.5.5`. Это подтверждает диагноз на уровне effective POM.

Второй момент: спецификация `build-configuration` уже требует, чтобы общие плагины объявлялись в `pluginManagement` родительского POM. Дублировать это требование в delta не нужно — новое требование касается только фактического выполнения тестов, чего в спеке описано не было.

Ограничение окружения: Maven 3.8.7 и Java 25. Surefire начиная с 3.x требует Maven не ниже 3.6.3, поэтому ограничение соблюдается.

## Goals / Non-Goals

**Goals:**
- Обеспечить фактический запуск всех unit-тестов при `mvn test` во всех модулях.
- Сохранить принятую архитектуру сборки: общая конфигурация только в родительском POM, дочерние модули её не дублируют.
- Не допустить расхождения версий с Spring Boot BOM при обновлении Spring Boot.
- Зафиксировать в коде комментарием причину, по которой версию приходится задавать явно, — иначе следующий разработчик посчитает её дублированием BOM и удалит.

**Non-Goals:**
- Не фиксировать версию JUnit в `dependencyManagement`. Она управляется BOM и подобрана под Spring Boot.
- Не добавлять `maven-failsafe-plugin`: интеграционных тестов в проекте нет.
- Не переводить сборку на родителя `spring-boot-starter-parent` (см. D2).
- Не добавлять интеграционные тесты и не подключать Testcontainers.

## Decisions

### D1. Версия surefire задаётся в родительском `pluginManagement` через отдельное свойство

Выбран вариант: свойство `<maven-surefire-plugin.version>` в `<properties>` + блок `maven-surefire-plugin` в `pluginManagement` со ссылкой `${maven-surefire-plugin.version}`.

Почему через свойство, а не литерал: версия 3.5.5 совпадает с `maven-surefire-plugin.version` из Spring Boot BOM 4.0.6. При обновлении Spring Boot расхождение заметят по одному месту, а не по факту «тесты перестали запускаться».

Альтернативы:
- **Литерал `3.5.5` прямо в `pluginManagement`.** Работает, но теряется связь с BOM: версия выглядит произвольной, и при апгрейде её легко пропустить.
- **Не задавать версию, положиться на BOM.** Отброшено: не работает, `pluginManagement` из BOM не наследуется (см. Context).

### D2. Родителем остаётся собственный POM, а не `spring-boot-starter-parent`

Альтернатива: объявить `spring-boot-starter-parent` родителем — тогда его `pluginManagement` унаследуется целиком, и surefire получит версию автоматически.

Отброшено по трём причинам:
1. Проект сознательно не наследует этот родитель: в `pom.xml` прямо написано, что привязка `repackage` к фазе `package` выполняется вручную именно потому, что собственный родитель этого не делает. Смена родителя потребовала бы пересмотра этой настройки.
2. Потеря контроля: под управление Spring Boot ушли бы версии почти всех плагинов сборки (`resources`, `jar`, `clean` и др.), что противоречит существующему требованию спеки о централизации конфигурации в нашем POM.
3. Усложняется структура многомодульника: появляется `<relativePath/>` и вопрос двойного управления версиями.

Цена выбранного варианта — 8 строк XML и поясняющий комментарий. Считаем приемлемой.

### D3. Дочерние модули не трогаем: пустой блок `<plugin>` в модулях не нужен

Проверено экспериментом: `pluginManagement` родителя перекрывает версию плагина и для плагинов, которые Maven подключает сам по жизненному циклу. После добавления блока в родительский POM `mvn clean test` выполнил 23 теста (9 в auth-service, 14 в product-service) без единого изменения в `backend/*/pom.xml`.

Поэтому требование спеки «Child modules reference shared configuration without duplication» выполняется буквально: модули не объявляют surefire вообще.

### D4. Выбор версии 3.5.5, а не более свежей

Актуальные релизы на момент работы: 3.5.5, 3.5.6, 3.6.0 (последний — сентябрь 2026).

Проверено локально: и 3.5.5, и 3.6.0 запускают все 23 теста без ошибок. Выбран 3.5.5 по совпадению с версией из BOM. 3.6.0 вышел месяц назад и не имеет проверенного опыта эксплуатации; 3.5.6 — промежуточный баг-фикс и принципиальной разницы с 3.5.5 не даёт.

Решения «держаться на 3.5.x навсегда» не принимаем: при обновлении BOM правится одно свойство.

### D5. Комментарий в `pom.xml` — обязательная часть изменения

Причина неочевидна: раздел `pluginManagement` в BOM существует, но не наследуется при импорте. Без комментария правка выглядит дублированием и будет удалена при первом же «приведении в порядок» pom. Комментарий фиксирует и диагноз, и способ проверки (`mvn help:effective-pom`), чтобы это не пришлось выяснять заново.

## Risks / Trade-offs

- [Падение сборки на падающем тесте] → До изменения сборка была зелёной независимо от состояния тестов, поэтому падение может «внезапно» проявиться на CI. Ожидаемое поведение; при выявлении падающего теста его нужно либо починить, либо явно исключить через `@Disabled` с причиной.
- [Расхождение с BOM при обновлении Spring Boot] → Версия вынесена в одно свойство с комментарием о происхождении. Проверка — сверка свойства с `maven-surefire-plugin.version` в новом BOM.
- [Дрейф в сторону более старого surefire] → Выбор 3.5.5 — сознательный компромисс в пользу совпадения с BOM. Осознанный апгрейд выполняется отдельной задачей с проверкой всех тестов.
- [Поведение `mvn package` тоже меняется] → Теперь падение теста провалит и `mvn package`. Это ожидаемо и соответствует требованию спеки, но стоит учитывать при локальной сборке.
